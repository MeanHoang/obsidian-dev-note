- **[Event-Driven Architecture: The Hard Parts — Three Dots Labs](https://threedots.tech/episode/event-driven-architecture/)** → 📝 Note chi tiết: [[dev-note/7 - Software Architecture/01 - Architectural Styles/Event-Driven/1 - The Hard Parts|Event-Driven Architecture - The Hard Parts]]
  **Đây là gì:** Bài đi sâu vào **pitfall production** của EDA (idempotency, ordering, replay, schema evolution) — không phải happy-path tutorial. EDA = service giao tiếp qua event thay vì gọi trực tiếp.
  **Vì sao đáng đọc:** Joy xử lý nhiều event async (order → points, refund → deduct). Hiểu pitfall trước khi adopt Pub/Sub rộng.
  **Key takeaways:**
  - **8 hard parts:** observability, eventual consistency, message loss, at-least-once delivery, poison messages, event design, distributed transactions, testing
  - **Outbox Pattern** = pattern must-know: ghi event vào cùng DB transaction với domain data, worker riêng publish lên broker → tránh dual-write problem
  - **Mọi handler PHẢI idempotent** (horror story: 10 triệu SMS gửi cho 1 số trong 10 phút vì broker redelivery + handler không idempotent)
  - **Event nhỏ, cụ thể** > event to, generic (event to không thể refactor khi nhiều team đã depend)
  - **Default là sync, không phải async** — chỉ migrate EDA khi có pain point cụ thể (external API chậm, heavy compute, fan-out, traffic spike)
  - **Tránh distributed transaction (saga)** — nếu cần saga giữa 3 service thì merge lại 1 service tốt hơn
  - Apply Joy: webhook handler phải check `X-Shopify-Webhook-Id` + `updated_at` trước khi process (Shopify webhook = at-least-once + no ordering)
- **[Event-Driven Architectural Patterns — ByteByteGo](https://blog.bytebytego.com/p/event-driven-architectural-patterns)** → 📝 Note chi tiết: [[EDA-Architectural-Patterns]]
  **Đây là gì:** Tổng hợp pattern EDA: Event Notification, Event-Carried State Transfer, Event Sourcing, CQRS — kèm ưu nhược từng cái.
  **Vì sao đáng đọc:** Reference ngắn để chọn đúng pattern cho từng case thực tế trong Joy.
  **Key takeaways:**
  - **Event Notification**: broadcast "có chuyện xảy ra", consumer tự quyết định — coupling thấp nhất nhưng hidden flow khó debug
  - **Event-Carried State Transfer**: event chứa full data → consumer lưu local copy, không call back source — high availability nhưng data duplication
  - **Event Sourcing**: event log = source of truth, state = replay events — audit mạnh nhưng complexity cao, schema evolution khó
  - **CQRS**: tách model read/write → read-heavy scale tốt, nhưng bị **misuse nhiều nhất** theo Fowler
  - **Không bắt buộc chọn 1** — 1 hệ thống có thể dùng nhiều pattern cho context khác nhau
  - Apply Joy: Notification cho user-signed-up / ECST cho Shopify order / Event Sourcing cho points history / CQRS cho merchant dashboard
