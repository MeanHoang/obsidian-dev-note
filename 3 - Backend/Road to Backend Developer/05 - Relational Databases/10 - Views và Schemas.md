# PHẦN A — VIEWS

## 1. View là gì, vì sao dùng

📖 **Nguyên văn** — PostgreSQL Documentation, *3.2. Views*
> "Refer back to the queries in Section 2.6. Suppose the combined listing of weather records and city location is of particular interest to your application, but you do not want to type the query each time you need it. You can create a view over the query, which gives a name to the query that you can refer to like an ordinary table:"

🇻🇳 **Dịch**
> "Hãy xem lại các query ở Mục 2.6. Giả sử danh sách kết hợp giữa các bản ghi thời tiết và vị trí thành phố đặc biệt hữu ích cho application của bạn, nhưng bạn không muốn phải gõ lại query đó mỗi lần cần dùng. Bạn có thể tạo một view trên query đó, việc này **đặt một cái tên cho query** để bạn tham chiếu tới nó như một table thông thường:"

```sql
CREATE VIEW myview AS
    SELECT name, temp_lo, temp_hi, prcp, date, location
        FROM weather, cities
        WHERE city = name;

SELECT * FROM myview;
```

🇻🇳 Câu lệnh trên tạo view `myview` gói sẵn phép join giữa `weather` và `cities`, sau đó truy vấn view y như truy vấn một table.

📖 **Nguyên văn** — PostgreSQL Documentation, *3.2. Views* (đoạn nói về việc đóng gói query phức tạp sau một cái tên)
> "Making liberal use of views is a key aspect of good SQL database design. Views allow you to encapsulate the details of the structure of your tables, which might change as your application evolves, behind consistent interfaces.
>
> Views can be used in almost any place a real table can be used. Building views upon other views is not uncommon."

🇻🇳 **Dịch**
> "Sử dụng view một cách rộng rãi là một khía cạnh then chốt của thiết kế SQL database tốt. View cho phép bạn **đóng gói (encapsulate) các chi tiết về cấu trúc của table** — thứ có thể thay đổi khi application của bạn tiến hoá — **đằng sau những interface nhất quán**.
>
> View có thể được dùng ở hầu hết mọi nơi mà một table thật có thể được dùng. Việc xây view trên nền các view khác không phải là hiếm."

💡 **Ví dụ đời sống**
View giống như **một ô cửa sổ nhìn vào căn phòng dữ liệu**. Ô cửa sổ không chứa đồ đạc — nó chỉ cho bạn thấy một phần căn phòng, theo một góc nhìn đã được cắt sẵn. Nếu trong phòng có người dọn dẹp, đổi chỗ bàn ghế (schema của table thay đổi), bạn vẫn nhìn qua **đúng ô cửa sổ cũ** và thấy đúng thứ mình cần — miễn là người lắp cửa sổ chỉnh lại hướng kính. Người đứng ngoài không cần biết bên trong phòng được sắp xếp thế nào.

## 2. CREATE VIEW — cú pháp đầy đủ

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Synopsis*
> ```
> CREATE [ OR REPLACE ] [ TEMP | TEMPORARY ] [ RECURSIVE ] VIEW name [ ( column_name [, ...] ) ]
>     [ WITH ( view_option_name [= view_option_value] [, ... ] ) ]
>     AS query
>     [ WITH [ CASCADED | LOCAL ] CHECK OPTION ]
> ```

🇻🇳 Đây là cú pháp gốc của lệnh `CREATE VIEW`: đặt tên view, (tuỳ chọn) đặt lại tên column, rồi `AS query`. `OR REPLACE` để ghi đè view cùng tên; `TEMP` tạo view tạm; `CHECK OPTION` kiểm soát hành vi ghi dữ liệu qua view (xem mục 3).

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Description*
> "CREATE VIEW defines a view of a query. The view is not physically materialized. Instead, the query is run every time the view is referenced in a query."

🇻🇳 **Dịch**
> "`CREATE VIEW` định nghĩa một view của một query. View **không được materialize về mặt vật lý**. Thay vào đó, query được chạy lại **mỗi lần** view được tham chiếu trong một query."

> [!note] Đây chính là điểm phân biệt cốt lõi với materialized view ở mục 4: view thường **không lưu dữ liệu**, chỉ lưu **câu query**.

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Description*
> "CREATE OR REPLACE VIEW is similar, but if a view of the same name already exists, it is replaced. The new query must generate the same columns that were generated by the existing view query (that is, the same column names in the same order and with the same data types), but it may add additional columns to the end of the list. The calculations giving rise to the output columns may be completely different."

🇻🇳 **Dịch**
> "`CREATE OR REPLACE VIEW` thì tương tự, nhưng nếu đã tồn tại một view cùng tên thì view đó sẽ bị thay thế. Query mới phải sinh ra **đúng các column** mà query của view cũ đã sinh ra (nghĩa là cùng tên column, cùng thứ tự, cùng data type), nhưng nó **có thể thêm column mới vào cuối** danh sách. Các phép tính tạo ra những output column đó thì có thể hoàn toàn khác."

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Description*
> "If a schema name is given (for example, CREATE VIEW myschema.myview ...) then the view is created in the specified schema. Otherwise it is created in the current schema. Temporary views exist in a special schema, so a schema name cannot be given when creating a temporary view. The name of the view must be distinct from the name of any other relation (table, sequence, index, view, materialized view, or foreign table) in the same schema."

🇻🇳 **Dịch**
> "Nếu có chỉ định tên schema (ví dụ `CREATE VIEW myschema.myview ...`) thì view được tạo trong schema đó. Ngược lại nó được tạo trong **current schema**. Temporary view nằm trong một schema đặc biệt, nên không thể chỉ định tên schema khi tạo temporary view. Tên của view phải khác với tên của mọi relation khác (table, sequence, index, view, materialized view, hoặc foreign table) **trong cùng schema**."

> [!tip] Câu cuối là cầu nối sang Phần B: table, index, view… **dùng chung một namespace** bên trong một schema. Xem mục 7.

## 3. View có cập nhật được không — Updatable Views

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Updatable Views*
> "Simple views are automatically updatable: the system will allow INSERT, UPDATE, DELETE, and MERGE statements to be used on the view in the same way as on a regular table. A view is automatically updatable if it satisfies all of the following conditions:
>
> - The view must have exactly one entry in its FROM list, which must be a table or another updatable view.
> - The view definition must not contain WITH, DISTINCT, GROUP BY, HAVING, LIMIT, or OFFSET clauses at the top level.
> - The view definition must not contain set operations (UNION, INTERSECT or EXCEPT) at the top level.
> - The view's select list must not contain any aggregates, window functions or set-returning functions."

🇻🇳 **Dịch**
> "Các view đơn giản **tự động có thể cập nhật được**: hệ thống sẽ cho phép dùng các statement `INSERT`, `UPDATE`, `DELETE` và `MERGE` trên view giống hệt như trên một table thông thường. Một view là automatically updatable nếu nó thoả **tất cả** các điều kiện sau:
>
> - View phải có **đúng một** entry trong danh sách `FROM`, và entry đó phải là một table hoặc một updatable view khác.
> - Định nghĩa view không được chứa các mệnh đề `WITH`, `DISTINCT`, `GROUP BY`, `HAVING`, `LIMIT`, hay `OFFSET` ở top level.
> - Định nghĩa view không được chứa các phép toán tập hợp (`UNION`, `INTERSECT` hoặc `EXCEPT`) ở top level.
> - Danh sách select của view không được chứa bất kỳ aggregate, window function hay set-returning function nào."

> [!note] Nói cách khác: view chỉ "ghi được" khi nó là **một lát cắt phẳng của đúng một table**. Hễ có `JOIN` nhiều bảng, `GROUP BY`, hay aggregate (xem [[03 - Queries - SELECT, JOIN, Aggregate]]) thì PostgreSQL không tự suy ra được phải ghi vào đâu.

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Updatable Views*
> "If the view is automatically updatable the system will convert any INSERT, UPDATE, DELETE, or MERGE statement on the view into the corresponding statement on the underlying base relation. INSERT statements that have an ON CONFLICT UPDATE clause are fully supported."

🇻🇳 **Dịch**
> "Nếu view là automatically updatable, hệ thống sẽ **chuyển đổi** mọi statement `INSERT`, `UPDATE`, `DELETE` hoặc `MERGE` trên view thành statement tương ứng trên base relation nằm dưới. Các statement `INSERT` có mệnh đề `ON CONFLICT UPDATE` được hỗ trợ đầy đủ."

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Updatable Views*
> "An automatically updatable view may contain a mix of updatable and non-updatable columns. A column is updatable if it is a simple reference to an updatable column of the underlying base relation; otherwise the column is read-only, and an error will be raised if an INSERT, UPDATE, or MERGE statement attempts to assign a value to it."

🇻🇳 **Dịch**
> "Một automatically updatable view có thể chứa lẫn lộn cả column cập nhật được lẫn column không cập nhật được. Một column là updatable nếu nó là **tham chiếu đơn giản** tới một column updatable của base relation bên dưới; ngược lại column đó là read-only, và sẽ phát sinh lỗi nếu một statement `INSERT`, `UPDATE` hay `MERGE` cố gán giá trị cho nó."

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE VIEW*, mục *Parameters* → `WITH [ CASCADED | LOCAL ] CHECK OPTION`
> "This option controls the behavior of automatically updatable views. When this option is specified, INSERT, UPDATE, and MERGE commands on the view will be checked to ensure that new rows satisfy the view-defining condition (that is, the new rows are checked to ensure that they are visible through the view). If they are not, the update will be rejected. If the CHECK OPTION is not specified, INSERT, UPDATE, and MERGE commands on the view are allowed to create rows that are not visible through the view."

🇻🇳 **Dịch**
> "Tuỳ chọn này điều khiển hành vi của các automatically updatable view. Khi tuỳ chọn này được chỉ định, các lệnh `INSERT`, `UPDATE` và `MERGE` trên view sẽ được kiểm tra để đảm bảo các row mới thoả điều kiện định nghĩa view (tức là các row mới được kiểm tra để chắc chắn chúng **nhìn thấy được qua view**). Nếu không thoả, lệnh cập nhật sẽ bị từ chối. Nếu không chỉ định `CHECK OPTION`, các lệnh `INSERT`, `UPDATE` và `MERGE` trên view **được phép tạo ra những row không nhìn thấy được qua view**."

> [!warning] Không có `CHECK OPTION`, bạn có thể `INSERT` qua một view rồi… không thấy row vừa insert đâu cả, vì nó rơi ra ngoài điều kiện `WHERE` của view.

## 4. Materialized View

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "Materialized views in PostgreSQL use the rule system like views do, but persist the results in a table-like form. The main differences between:"

🇻🇳 **Dịch**
> "Materialized view trong PostgreSQL dùng rule system giống như view thường, nhưng **lưu lại (persist) kết quả dưới dạng giống một table**. Những khác biệt chính giữa:"

```sql
CREATE MATERIALIZED VIEW mymatview AS SELECT * FROM mytab;
```

🇻🇳 Lệnh tạo materialized view `mymatview` — chạy query một lần và **lưu kết quả xuống đĩa**.

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "and:"

🇻🇳 **Dịch**
> "và:"

```sql
CREATE TABLE mymatview AS SELECT * FROM mytab;
```

🇻🇳 Lệnh tạo một table thường từ kết quả query — cũng lưu dữ liệu, nhưng **không nhớ query gốc**.

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "are that the materialized view cannot subsequently be directly updated and that the query used to create the materialized view is stored in exactly the same way that a view's query is stored, so that fresh data can be generated for the materialized view with:"

🇻🇳 **Dịch**
> "…là ở chỗ materialized view **không thể bị cập nhật trực tiếp** về sau, và câu query dùng để tạo materialized view **được lưu lại y hệt cách query của một view được lưu**, nhờ đó có thể sinh ra dữ liệu mới cho materialized view bằng:"

```sql
REFRESH MATERIALIZED VIEW mymatview;
```

🇻🇳 Lệnh này chạy lại query gốc và ghi đè toàn bộ nội dung đã lưu của materialized view bằng dữ liệu mới nhất.

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "The information about a materialized view in the PostgreSQL system catalogs is exactly the same as it is for a table or view. So for the parser, a materialized view is a relation, just like a table or a view. When a materialized view is referenced in a query, the data is returned directly from the materialized view, like from a table; the rule is only used for populating the materialized view."

🇻🇳 **Dịch**
> "Thông tin về một materialized view trong system catalog của PostgreSQL hoàn toàn giống như đối với một table hay một view. Vì vậy với parser, materialized view là một **relation**, y như table hay view. Khi materialized view được tham chiếu trong một query, **dữ liệu được trả về trực tiếp từ materialized view, như lấy từ một table**; rule chỉ được dùng để nạp dữ liệu cho materialized view."

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "While access to the data stored in a materialized view is often much faster than accessing the underlying tables directly or through a view, the data is not always current; yet sometimes current data is not needed. Consider a table which records sales:"

🇻🇳 **Dịch**
> "Trong khi việc truy cập dữ liệu lưu trong materialized view thường **nhanh hơn nhiều** so với truy cập trực tiếp các table bên dưới hoặc qua một view, thì dữ liệu **không phải lúc nào cũng mới**; tuy vậy đôi khi ta không cần dữ liệu mới nhất. Hãy xét một table ghi lại doanh số:"

```sql
CREATE TABLE invoice (
    invoice_no    integer        PRIMARY KEY,
    seller_no     integer,       -- ID of salesperson
    invoice_date  date,          -- date of sale
    invoice_amt   numeric(13,2)  -- amount of sale
);
```

🇻🇳 Table hoá đơn với `PRIMARY KEY` là số hoá đơn (xem [[02 - Tables, Data Types và Constraints]]), cùng mã nhân viên bán hàng, ngày bán và số tiền.

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "If people want to be able to quickly graph historical sales data, they might want to summarize, and they may not care about the incomplete data for the current date:"

🇻🇳 **Dịch**
> "Nếu người dùng muốn vẽ biểu đồ dữ liệu doanh số lịch sử một cách nhanh chóng, họ có thể muốn tổng hợp lại, và họ có thể không quan tâm tới phần dữ liệu chưa đầy đủ của ngày hiện tại:"

```sql
CREATE MATERIALIZED VIEW sales_summary AS
  SELECT
      seller_no,
      invoice_date,
      sum(invoice_amt)::numeric(13,2) as sales_amt
    FROM invoice
    WHERE invoice_date < CURRENT_DATE
    GROUP BY
      seller_no,
      invoice_date;

CREATE UNIQUE INDEX sales_summary_seller
  ON sales_summary (seller_no, invoice_date);
```

🇻🇳 Tạo materialized view tổng hợp doanh số theo từng nhân viên + từng ngày (bỏ qua ngày hôm nay), rồi **tạo index ngay trên materialized view** đó — điều mà view thường không làm được.

📖 **Nguyên văn** — PostgreSQL Documentation, *39.3. Materialized Views*
> "This materialized view might be useful for displaying a graph in the dashboard created for salespeople. A job could be scheduled to update the statistics each night using this SQL statement:"

🇻🇳 **Dịch**
> "Materialized view này có thể hữu ích để hiển thị một biểu đồ trong dashboard làm cho nhân viên bán hàng. Có thể lập lịch một job để cập nhật số liệu thống kê **mỗi đêm** bằng statement SQL sau:"

```sql
REFRESH MATERIALIZED VIEW sales_summary;
```

🇻🇳 Chạy lại toàn bộ query tổng hợp và nạp lại dữ liệu cho `sales_summary`.

### 4.1. Cú pháp CREATE MATERIALIZED VIEW

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE MATERIALIZED VIEW*, mục *Synopsis*
> ```
> CREATE MATERIALIZED VIEW [ IF NOT EXISTS ] table_name
>     [ (column_name [, ...] ) ]
>     [ USING method ]
>     [ WITH ( storage_parameter [= value] [, ... ] ) ]
>     [ TABLESPACE tablespace_name ]
>     AS query
>     [ WITH [ NO ] DATA ]
> ```

🇻🇳 Cú pháp gốc. Đáng chú ý: có `TABLESPACE` và `storage_parameter` — những thứ chỉ table thật mới có, khẳng định materialized view **chiếm chỗ trên đĩa**. `WITH NO DATA` tạo view rỗng, chưa chạy query.

📖 **Nguyên văn** — PostgreSQL Documentation, *CREATE MATERIALIZED VIEW*, mục *Description*
> "CREATE MATERIALIZED VIEW defines a materialized view of a query. The query is executed and used to populate the view at the time the command is issued (unless WITH NO DATA is used) and may be refreshed later using REFRESH MATERIALIZED VIEW.
>
> CREATE MATERIALIZED VIEW is similar to CREATE TABLE AS, except that it also remembers the query used to initialize the view, so that it can be refreshed later upon demand. A materialized view has many of the same properties as a table, but there is no support for temporary materialized views."

🇻🇳 **Dịch**
> "`CREATE MATERIALIZED VIEW` định nghĩa một materialized view của một query. Query được thực thi và dùng để nạp dữ liệu cho view **ngay tại thời điểm ra lệnh** (trừ khi dùng `WITH NO DATA`), và có thể được refresh về sau bằng `REFRESH MATERIALIZED VIEW`.
>
> `CREATE MATERIALIZED VIEW` tương tự `CREATE TABLE AS`, chỉ khác ở chỗ nó còn **ghi nhớ câu query** đã dùng để khởi tạo view, nhờ đó có thể refresh lại khi cần. Materialized view có nhiều thuộc tính giống table, nhưng **không hỗ trợ temporary materialized view**."

💡 **Ví dụ đời sống**
Nếu view thường là **ô cửa sổ** (nhìn qua là thấy tình trạng phòng ngay lúc đó), thì materialized view là **tấm ảnh chụp căn phòng treo ngoài hành lang**. Nhìn ảnh thì **nhanh tức thì** — không cần mở cửa, không cần đi vào phòng. Đổi lại, ảnh chỉ đúng với khoảnh khắc chụp; phòng có xê dịch gì sau đó ảnh cũng không biết. Muốn ảnh khớp lại với thực tế thì phải **chụp lại** — đó chính là `REFRESH MATERIALIZED VIEW`.

## 5. Bảng so sánh View vs Materialized View

| Tiêu chí | View | Materialized View |
|---|---|---|
| Lưu dữ liệu trên đĩa | Không — "The view is not physically materialized." | Có — "persist the results in a table-like form" |
| Cái được lưu lại | Câu query | Câu query **và** kết quả của nó |
| Khi được truy vấn | "the query is run every time the view is referenced in a query" | "the data is returned directly from the materialized view, like from a table" |
| Độ mới của dữ liệu | Luôn mới (tính lại mỗi lần) | "the data is not always current" — chỉ mới tới lần refresh gần nhất |
| Tốc độ đọc | Phụ thuộc query gốc | "often much faster than accessing the underlying tables directly or through a view" |
| Ghi dữ liệu | Được, nếu là *automatically updatable view* (mục 3) | "cannot subsequently be directly updated" |
| Làm mới | Không cần | `REFRESH MATERIALIZED VIEW` |
| Tạo index lên trên | — | Được (ví dụ `CREATE UNIQUE INDEX sales_summary_seller ...`) |
| Temporary | Có — `TEMP` / `TEMPORARY` trong `CREATE VIEW` | "there is no support for temporary materialized views" |

> [!tip] Quy tắc chọn rút ra từ tài liệu: cần **dữ liệu luôn đúng thời điểm** → view. Chấp nhận dữ liệu trễ một nhịp để đổi lấy tốc độ đọc (dashboard, báo cáo, biểu đồ lịch sử) → materialized view + job refresh định kỳ.

# PHẦN B — SCHEMAS

## 6. Database → schema → table

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10. Schemas*
> "A PostgreSQL database cluster contains one or more named databases. Roles and a few other object types are shared across the entire cluster. A client connection to the server can only access data in a single database, the one specified in the connection request."

🇻🇳 **Dịch**
> "Một database cluster của PostgreSQL chứa **một hoặc nhiều database có tên**. Role và một vài loại object khác được dùng chung trên toàn bộ cluster. Một client connection tới server **chỉ có thể truy cập dữ liệu trong đúng một database**, chính là database được chỉ định trong connection request."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10. Schemas*
> "A database contains one or more named schemas, which in turn contain tables. Schemas also contain other kinds of named objects, including data types, functions, and operators. Within one schema, two objects of the same type cannot have the same name. Furthermore, tables, sequences, indexes, views, materialized views, and foreign tables share the same namespace, so that, for example, an index and a table must have different names if they are in the same schema. The same object name can be used in different schemas without conflict; for example, both schema1 and myschema can contain tables named mytable. Unlike databases, schemas are not rigidly separated: a user can access objects in any of the schemas in the database they are connected to, if they have privileges to do so."

🇻🇳 **Dịch**
> "Một database chứa **một hoặc nhiều schema có tên**, và các schema này lần lượt chứa **table**. Schema cũng chứa các loại object có tên khác, gồm data type, function và operator. Trong cùng một schema, hai object cùng loại không thể trùng tên. Hơn nữa, table, sequence, index, view, materialized view và foreign table **dùng chung một namespace**, nên ví dụ một index và một table phải có tên khác nhau nếu chúng nằm trong cùng một schema. Cùng một tên object **có thể được dùng ở các schema khác nhau mà không xung đột**; ví dụ, cả `schema1` lẫn `myschema` đều có thể chứa table tên `mytable`. Khác với database, các schema **không bị tách biệt cứng nhắc**: một user có thể truy cập object ở bất kỳ schema nào trong database mà họ đang kết nối tới, nếu họ có privilege để làm điều đó."

Tóm lại thứ tự lồng nhau: **cluster → database → schema → table** (và view, materialized view, index, sequence…).

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10. Schemas*
> "Schemas are analogous to directories at the operating system level, except that schemas cannot be nested."

🇻🇳 **Dịch**
> "Schema **tương tự như các thư mục (directory) ở cấp hệ điều hành**, chỉ khác ở chỗ schema **không thể lồng nhau**."

💡 **Ví dụ đời sống**
Chính tài liệu đã đưa ra ví von này, và nó rất sát: schema là **thư mục trong ổ đĩa**. Trong `/report/` và `/backup/` đều có thể có file `data.csv` mà không đụng nhau — hệt như `schema1.mytable` và `myschema.mytable`. Khác biệt duy nhất: thư mục thật thì lồng được nhiều tầng (`/a/b/c/`), còn schema **chỉ có đúng một tầng**.

## 7. Vì sao dùng schema

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10. Schemas*
> "There are several reasons why one might want to use schemas:
>
> - To allow many users to use one database without interfering with each other.
> - To organize database objects into logical groups to make them more manageable.
> - Third-party applications can be put into separate schemas so they do not collide with the names of other objects."

🇻🇳 **Dịch**
> "Có vài lý do khiến người ta muốn dùng schema:
>
> - Để **nhiều user cùng dùng một database mà không cản trở nhau**.
> - Để **tổ chức các database object thành những nhóm logic**, giúp chúng dễ quản lý hơn.
> - Các third-party application có thể được đặt vào các schema riêng để chúng **không đụng tên** với các object khác."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.6. Usage Patterns*
> "For any pattern, to install shared applications (tables to be used by everyone, additional functions provided by third parties, etc.), put them into separate schemas. Remember to grant appropriate privileges to allow the other users to access them. Users can then refer to these additional objects by qualifying the names with a schema name, or they can put the additional schemas into their search path, as they choose."

🇻🇳 **Dịch**
> "Với bất kỳ pattern nào, để cài đặt các shared application (table dùng chung cho mọi người, function bổ sung do bên thứ ba cung cấp, v.v.), hãy đặt chúng vào **các schema riêng biệt**. Nhớ cấp privilege phù hợp để cho phép các user khác truy cập chúng. Sau đó user có thể tham chiếu tới những object bổ sung này bằng cách **ghi tên đủ điều kiện kèm tên schema**, hoặc đưa các schema đó vào `search_path` của mình, tuỳ họ chọn."

## 10. `search_path` — PostgreSQL tìm table thế nào khi không ghi rõ schema

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "Qualified names are tedious to write, and it's often best not to wire a particular schema name into applications anyway. Therefore tables are often referred to by unqualified names, which consist of just the table name. The system determines which table is meant by following a search path, which is a list of schemas to look in. The first matching table in the search path is taken to be the one wanted. If there is no match in the search path, an error is reported, even if matching table names exist in other schemas in the database."

🇻🇳 **Dịch**
> "Qualified name viết ra thì rườm rà, và nói chung cũng không nên gắn cứng một tên schema cụ thể vào application. Vì vậy table thường được tham chiếu bằng **unqualified name** — chỉ gồm tên table. Hệ thống xác định table nào được nhắc tới bằng cách đi theo một **search path**, tức là **một danh sách các schema cần tìm trong đó**. **Table khớp đầu tiên** trong search path được coi là table cần tìm. Nếu không có gì khớp trong search path, một lỗi sẽ được báo, **kể cả khi** có những tên table khớp ở các schema khác trong database."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "The first schema named in the search path is called the current schema. Aside from being the first schema searched, it is also the schema in which new tables will be created if the CREATE TABLE command does not specify a schema name."

🇻🇳 **Dịch**
> "Schema được nêu đầu tiên trong search path được gọi là **current schema**. Ngoài việc là schema được tìm đầu tiên, nó còn là schema mà **các table mới sẽ được tạo trong đó** nếu lệnh `CREATE TABLE` không chỉ định tên schema."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "To show the current search path, use the following command:"

🇻🇳 **Dịch**
> "Để xem search path hiện tại, dùng lệnh sau:"

```sql
SHOW search_path;
```

🇻🇳 In ra danh sách schema mà PostgreSQL sẽ tìm theo thứ tự.

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "In the default setup this returns:"
> ```
>  search_path
> --------------
>  "$user", public
> ```

🇻🇳 **Dịch**
> "Với thiết lập mặc định, lệnh này trả về:" — tức search path mặc định gồm hai phần tử: `"$user"` rồi tới `public`.

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "The first element specifies that a schema with the same name as the current user is to be searched. If no such schema exists, the entry is ignored. The second element refers to the public schema that we have seen already.
>
> The first schema in the search path that exists is the default location for creating new objects. That is the reason that by default objects are created in the public schema. When objects are referenced in any other context without schema qualification (table modification, data modification, or query commands) the search path is traversed until a matching object is found. Therefore, in the default configuration, any unqualified access again can only refer to the public schema."

🇻🇳 **Dịch**
> "Phần tử đầu tiên chỉ định rằng **một schema trùng tên với user hiện tại** sẽ được tìm. Nếu không tồn tại schema như vậy, entry đó bị bỏ qua. Phần tử thứ hai trỏ tới schema `public` mà ta đã thấy.
>
> **Schema đầu tiên trong search path mà thực sự tồn tại** là nơi mặc định để tạo object mới. Đó là lý do vì sao mặc định các object được tạo trong schema `public`. Khi object được tham chiếu trong bất kỳ ngữ cảnh nào khác mà không ghi rõ schema (lệnh sửa table, sửa dữ liệu, hay query), search path **được duyệt cho tới khi tìm thấy object khớp**. Vì vậy, trong cấu hình mặc định, mọi truy cập không ghi rõ schema lại chỉ có thể trỏ tới schema `public`."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "To put our new schema in the path, we use:"

🇻🇳 **Dịch**
> "Để đưa schema mới của chúng ta vào path, ta dùng:"

```sql
SET search_path TO myschema,public;
```

🇻🇳 Đặt search path thành `myschema` trước, rồi mới tới `public`.

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "(We omit the $user here because we have no immediate need for it.) And then we can access the table without schema qualification:"

🇻🇳 **Dịch**
> "(Ở đây ta bỏ `$user` vì chưa cần tới nó ngay.) Và sau đó ta có thể truy cập table mà không cần ghi rõ schema:"

```sql
DROP TABLE mytable;
```

🇻🇳 Xoá `myschema.mytable` mà chỉ cần viết `mytable`, nhờ search path.

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path*
> "Also, since myschema is the first element in the path, new objects would by default be created in it."

🇻🇳 **Dịch**
> "Ngoài ra, vì `myschema` là phần tử đầu tiên trong path, các object mới **mặc định sẽ được tạo trong nó**."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.3. The Schema Search Path* (cảnh báo bảo mật)
> "The ability to create like-named objects in different schemas complicates writing a query that references precisely the same objects every time. It also opens up the potential for users to change the behavior of other users' queries, maliciously or accidentally. Due to the prevalence of unqualified names in queries and their use in PostgreSQL internals, adding a schema to search_path effectively trusts all users having CREATE privilege on that schema. When you run an ordinary query, a malicious user able to create objects in a schema of your search path can take control and execute arbitrary SQL functions as though you executed them."

🇻🇳 **Dịch**
> "Khả năng tạo các object trùng tên ở những schema khác nhau khiến việc viết một query luôn tham chiếu **chính xác cùng những object** trở nên phức tạp. Nó cũng mở ra khả năng user này **thay đổi hành vi query của user khác**, dù cố ý hay vô tình. Do unqualified name được dùng phổ biến trong query và trong nội bộ PostgreSQL, việc thêm một schema vào `search_path` **thực chất là tin tưởng toàn bộ user có privilege `CREATE` trên schema đó**. Khi bạn chạy một query bình thường, một user độc hại có khả năng tạo object trong một schema thuộc search path của bạn có thể chiếm quyền và thực thi các SQL function tuỳ ý **như thể chính bạn thực thi chúng**."

> [!warning] Thêm schema vào `search_path` = tin tưởng mọi user có quyền `CREATE` trên schema đó. Đây là lý do tài liệu khuyến nghị *secure schema usage pattern* ở mục 5.10.6.

### 10.1. `pg_catalog` luôn nằm trong search path

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.5. The System Catalog Schema*
> "In addition to public and user-created schemas, each database contains a pg_catalog schema, which contains the system tables and all the built-in data types, functions, and operators. pg_catalog is always effectively part of the search path. If it is not named explicitly in the path then it is implicitly searched before searching the path's schemas. This ensures that built-in names will always be findable. However, you can explicitly place pg_catalog at the end of your search path if you prefer to have user-defined names override built-in names."

🇻🇳 **Dịch**
> "Ngoài `public` và các schema do user tạo, mỗi database còn chứa một schema `pg_catalog`, nơi chứa các system table cùng toàn bộ data type, function và operator dựng sẵn. `pg_catalog` **luôn được coi là một phần của search path**. Nếu nó không được nêu tên tường minh trong path thì nó được tìm **ngầm định, trước** các schema trong path. Điều này đảm bảo các tên dựng sẵn luôn tìm thấy được. Tuy nhiên, bạn có thể đặt `pg_catalog` tường minh ở **cuối** search path nếu muốn các tên do user định nghĩa ghi đè lên tên dựng sẵn."

## 11. Một vài usage pattern của schema

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.6. Usage Patterns*
> "Constrain ordinary users to user-private schemas. To implement this pattern, first ensure that no schemas have public CREATE privileges. Then, for every user needing to create non-temporary objects, create a schema with the same name as that user, for example CREATE SCHEMA alice AUTHORIZATION alice. (Recall that the default search path starts with $user, which resolves to the user name. Therefore, if each user has a separate schema, they access their own schemas by default.)"

🇻🇳 **Dịch**
> "**Giới hạn các user thông thường vào những schema riêng của từng user.** Để triển khai pattern này, trước hết đảm bảo không schema nào có privilege `CREATE` công khai. Sau đó, với mỗi user cần tạo object không tạm thời, hãy tạo một schema **trùng tên với user đó**, ví dụ `CREATE SCHEMA alice AUTHORIZATION alice`. (Nhớ rằng search path mặc định bắt đầu bằng `$user`, và `$user` phân giải ra tên user. Do đó, nếu mỗi user có một schema riêng, mặc định họ sẽ truy cập chính schema của mình.)"

📖 **Nguyên văn** — PostgreSQL Documentation, *5.10.6. Usage Patterns*
> "Keep the default search path, and grant privileges to create in the public schema. All users access the public schema implicitly. This simulates the situation where schemas are not available at all, giving a smooth transition from the non-schema-aware world. However, this is never a secure pattern. It is acceptable only when the database has a single user or a few mutually-trusting users. In databases upgraded from PostgreSQL 14 or earlier, this is the default."

🇻🇳 **Dịch**
> "**Giữ nguyên search path mặc định, và cấp privilege để tạo object trong schema `public`.** Mọi user truy cập schema `public` một cách ngầm định. Cách này mô phỏng tình huống như thể không hề có schema, tạo bước chuyển mượt mà từ thế giới không biết tới schema. Tuy nhiên, **đây không bao giờ là một pattern an toàn**. Nó chỉ chấp nhận được khi database có một user duy nhất hoặc một vài user tin tưởng lẫn nhau. Ở các database được nâng cấp từ PostgreSQL 14 trở về trước, đây là mặc định."

# PHẦN C — PARTITIONING (giới thiệu)

> [!note] Đây **chỉ là phần giới thiệu khái niệm**, trích từ mục *5.12.1. Overview*. Nội dung chuyên sâu (declarative partitioning, partition pruning, best practices, và các chủ đề scaling liên quan như replication/sharding) thuộc về `11 - Advanced Backend/09 - Scaling Databases`.

## 12. Partitioning là gì

📖 **Nguyên văn** — PostgreSQL Documentation, *5.12. Table Partitioning*
> "PostgreSQL supports basic table partitioning. This section describes why and how to implement partitioning as part of your database design."

🇻🇳 **Dịch**
> "PostgreSQL hỗ trợ table partitioning cơ bản. Mục này mô tả **vì sao** và **bằng cách nào** triển khai partitioning như một phần trong thiết kế database của bạn."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.12.1. Overview*
> "Partitioning refers to splitting what is logically one large table into smaller physical pieces. Partitioning can provide several benefits:
>
> - Query performance can be improved dramatically in certain situations, particularly when most of the heavily accessed rows of the table are in a single partition or a small number of partitions. Partitioning effectively substitutes for the upper tree levels of indexes, making it more likely that the heavily-used parts of the indexes fit in memory.
> - When queries or updates access a large percentage of a single partition, performance can be improved by using a sequential scan of that partition instead of using an index, which would require random-access reads scattered across the whole table.
> - Bulk loads and deletes can be accomplished by adding or removing partitions, if the usage pattern is accounted for in the partitioning design. Dropping an individual partition using DROP TABLE, or doing ALTER TABLE DETACH PARTITION, is far faster than a bulk operation. These commands also entirely avoid the VACUUM overhead caused by a bulk DELETE.
> - Seldom-used data can be migrated to cheaper and slower storage media."

🇻🇳 **Dịch**
> "Partitioning nghĩa là **chia cái mà về mặt logic là một table lớn thành những mảnh vật lý nhỏ hơn**. Partitioning có thể mang lại vài lợi ích:
>
> - Hiệu năng query có thể cải thiện **rất mạnh** trong một số tình huống, đặc biệt khi phần lớn các row bị truy cập nhiều nằm trong **một partition hoặc một số ít partition**. Partitioning về cơ bản thay thế cho các tầng trên của cây index, làm tăng khả năng những phần index hay dùng **vừa trong bộ nhớ**.
> - Khi query hoặc update truy cập một tỉ lệ lớn của một partition đơn lẻ, hiệu năng có thể cải thiện bằng cách dùng **sequential scan** trên partition đó thay vì dùng index — vốn đòi hỏi các lượt đọc ngẫu nhiên rải rác khắp toàn bộ table.
> - Việc nạp và xoá dữ liệu hàng loạt có thể thực hiện bằng cách **thêm hoặc bỏ partition**, nếu pattern sử dụng đã được tính tới trong thiết kế partition. Xoá một partition riêng lẻ bằng `DROP TABLE`, hay dùng `ALTER TABLE DETACH PARTITION`, **nhanh hơn nhiều** so với một thao tác hàng loạt. Những lệnh này cũng tránh hoàn toàn chi phí `VACUUM` gây ra bởi một lệnh `DELETE` hàng loạt.
> - Dữ liệu ít dùng có thể được chuyển sang **thiết bị lưu trữ rẻ hơn và chậm hơn**."

> [!note] Lợi ích thứ nhất liên hệ trực tiếp với [[04 - Indexes]]: partitioning "thay thế cho các tầng trên của cây index".

📖 **Nguyên văn** — PostgreSQL Documentation, *5.12.1. Overview*
> "These benefits will normally be worthwhile only when a table would otherwise be very large. The exact point at which a table will benefit from partitioning depends on the application, although a rule of thumb is that the size of the table should exceed the physical memory of the database server."

🇻🇳 **Dịch**
> "Những lợi ích này thường **chỉ đáng giá khi table vốn dĩ rất lớn**. Ngưỡng chính xác mà tại đó một table bắt đầu hưởng lợi từ partitioning thì phụ thuộc vào application, tuy nhiên một **quy tắc ngón tay cái** là kích thước table nên **vượt quá bộ nhớ vật lý của database server**."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.12.1. Overview*
> "PostgreSQL offers built-in support for the following forms of partitioning:
>
> **Range Partitioning** — The table is partitioned into “ranges” defined by a key column or set of columns, with no overlap between the ranges of values assigned to different partitions. For example, one might partition by date ranges, or by ranges of identifiers for particular business objects. Each range's bounds are understood as being inclusive at the lower end and exclusive at the upper end. For example, if one partition's range is from 1 to 10, and the next one's range is from 10 to 20, then value 10 belongs to the second partition not the first.
>
> **List Partitioning** — The table is partitioned by explicitly listing which key value(s) appear in each partition.
>
> **Hash Partitioning** — The table is partitioned by specifying a modulus and a remainder for each partition. Each partition will hold the rows for which the hash value of the partition key divided by the specified modulus will produce the specified remainder."

🇻🇳 **Dịch**
> "PostgreSQL hỗ trợ sẵn các dạng partitioning sau:
>
> **Range Partitioning** — Table được chia thành các “khoảng” (range) định nghĩa bởi một key column hoặc một tập column, **không chồng lấn** giữa các khoảng giá trị gán cho những partition khác nhau. Ví dụ, ta có thể chia theo khoảng ngày tháng, hoặc theo khoảng identifier của những business object cụ thể. Biên của mỗi khoảng được hiểu là **bao gồm đầu dưới và loại trừ đầu trên**. Ví dụ, nếu khoảng của một partition là từ 1 tới 10, và khoảng của partition kế là từ 10 tới 20, thì giá trị 10 thuộc partition **thứ hai**, không phải thứ nhất.
>
> **List Partitioning** — Table được chia bằng cách **liệt kê tường minh** những giá trị key nào xuất hiện trong mỗi partition.
>
> **Hash Partitioning** — Table được chia bằng cách chỉ định một **modulus** và một **remainder** cho mỗi partition. Mỗi partition sẽ giữ những row mà giá trị hash của partition key chia cho modulus đã chỉ định sẽ cho ra remainder đã chỉ định."

📖 **Nguyên văn** — PostgreSQL Documentation, *5.12.1. Overview*
> "If your application needs to use other forms of partitioning not listed above, alternative methods such as inheritance and UNION ALL views can be used instead. Such methods offer flexibility but do not have some of the performance benefits of built-in declarative partitioning."

🇻🇳 **Dịch**
> "Nếu application của bạn cần dùng những dạng partitioning khác không liệt kê ở trên, có thể dùng các phương pháp thay thế như inheritance và các view kiểu `UNION ALL`. Những phương pháp đó linh hoạt hơn nhưng **không có được một số lợi ích hiệu năng** của declarative partitioning dựng sẵn."

💡 **Ví dụ đời sống**
Một cuốn sổ ghi chép 10 năm dày cộp, tra cứu gì cũng phải lật cả quyển. Partitioning là **xé ra thành 10 cuốn, mỗi năm một cuốn**. Cần số liệu năm 2023 thì rút đúng cuốn 2023 ra — khỏi động tới 9 cuốn kia. Muốn bỏ dữ liệu năm 2015 thì **vứt nguyên cuốn đó đi**, thay vì ngồi tẩy từng dòng (đúng ý "Dropping an individual partition using DROP TABLE… is far faster than a bulk operation"). Và các cuốn cũ ít tra thì cất xuống kho (storage rẻ hơn).
